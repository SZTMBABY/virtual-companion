## p1-3 新增 Live2D 渲染组件（WebView 承载）

**做了什么**：WebView 承载 `assets/l2d/render.html`，用 pixi.js 6.5.10 +
pixi-live2d-display 0.4.0（cubism4 构建）+ 官方 Cubism Core 5.1.0 渲染 moc3 v5 模型。
渲染层包在 `Live2DController` 后面（`setMouth`/`setSpeaking`/`setEmotion`/`setGaze`/`setView`/`reset`），
将来换 Native SDK 只替换这一个文件。

**改了哪些文件**：`ui/live2d/Live2DView.kt`、`ui/main/MainScreen.kt`、
`assets/l2d/render.html`、`MainActivity.kt`。

**怎么验证**（真机 `<device-serial>`，logcat tag `Live2DView`）：
```
Live2D Cubism Core version: 05.01.0000 (83951616)
L2D params {"ParamAngleX":27,...,"ParamEyeLOpen":14,"ParamMouthOpenY":18,"ParamBreath":37}
L2D layout canvas=400.8x534.2 half=false scale=0.10486 box=348.8x523.5
L2D_READY drawables=136
```
截图 `docs/proof/p1_main_port.png`（480×640，角色完整居中）。

**四个必须记住的渲染坑**（都已修进 `render.html`）：
1. `<script src>` 不能用 `l2d/pixi.min.js`——render.html 自己就在 `assets/l2d/` 下，写 `pixi.min.js`。
2. Cubism4ModelSettings **强制**要求 settings JSON 顶层有字符串 `url`，原模型包没有 → 必须注入。
3. `FileReferences` 里所有相对路径都要转成绝对（Moc / Textures / Physics / DisplayInfo /
   Expressions / Motions / Sound）。
4. `Groups.EyeBlink.Ids` 与 `Groups.LipSync.Ids` 在原包里是**空数组** → 必须补
   `['ParamEyeLOpen','ParamEyeROpen']` / `['ParamMouthOpenY']`，否则不眨眼不张嘴。

**黑屏真因**：`#stage{position:absolute;inset:0}` 在 Chromium 103 的 WebView 里把百分比高度
解析成 0，canvas 变成 h=0 的不可见元素（GL 照常渲染、readPixels 有像素，屏幕一片空白）。
修法：`position:fixed` + `applyCanvasSize()` 显式写 px，并给 `viewport()` 加兜底。

**抽搐/更快真因**：库里 `_render()` 已经用 `internalModel.update(deltaTime, elapsedTime)` 驱动，
第一个参数是**毫秒增量**、第二个是**毫秒累计**。我手写时传成 `update(nowMs, dtMs)`（反了），
累计时间被当成每帧增量喂给呼吸/摆动相位，于是越跑越快。
修法：不手动调 update，保持 `autoUpdate` 默认 true，把写参数挂在
`internalModel.on('beforeModelUpdate', ...)` 上（时序在 motion/expression/eyeblink 之后、
`coreModel.update()` 之前）。
验证：`L2D_JITTER2 updCalls=59 ticks=58 jumps={...全 0}`，每帧恰好一次 update。

**巨物真因**：`layout()` 不幂等——`getBounds()` 返回已乘 scale 的世界坐标，切前后台触发
resize 会再次放大 9.3 倍。修法：测量前 `model.scale.set(1); model.position.set(0,0)`。

**用户确认**：m01208「正常了」。

**新增需求（用户 m01154）**：半身模式。`DisplayConfig(halfBody=false, halfBodyRatio=0.48)`，
JS 侧 `view` + `layout()` 分支 + `__l2d.setView()` + URL 参数 `half=1&ratio=0.48`。
半身只按**高度**定缩放（允许左右溢出），因为该角色细长（3326×4992），
取 `min(CW/w, CH/(h*ratio))` 后宽度约束永远更紧，实测只放大 12%（0.10486 → 0.11810），
等于没效果；改成 `s = CH/(h*ratio)*0.98` 后实测 0.21847（2.08 倍），
渲染盒 726.6×1090.6，fps 28。截图 `docs/proof/p1_halfbody_port2.png`。

**有无偏离**：无。实现层调整：初版半身用 `min()` 导致无效，属实现 bug 而非口径变更。

## p1-4 限制渲染帧率为 24

**做了什么**：`render.html` 里设 `PIXI.Ticker.shared.maxFPS = 24`（可由 URL 参数 `fps` 覆盖，
默认 24）。用户 m01343 要求「限制帧率到24，避免卡顿」。

**为什么只改 Ticker 的 maxFPS**：`PIXI.Ticker.shared` 同时驱动 `_render()` 与库的
`onTickerUpdate → autoUpdate → internalModel.update`，所以一个开关能同时降渲染帧与模型动画帧，
不会出现「画面 24fps、动作 60fps」的错位。

**怎么验证**：logcat 出现 `L2D fps cap=24`；界面状态条 fps 从 28–29 降到 **22**（实测值略低于
24 是 WebView 与采样口径的正常差）。

**结果**：帧率稳定在 ~22fps。`dumpsys gfxinfo` 仍显示 91.69% janky，但那是 WebView
主线程统计口径（含合成与纹理上传），与用户可感知的动画平滑度不是一回事；
视觉最终判定权在用户（m01242）。

**有无偏离**：无。

## p2 接入 OpenAI 协议大模型（SSE 流式）

**做了什么**：
- `data/chat/ChatMessage.kt`：消息模型（role/content/seq）+ `SayExtractor`（流式半截 JSON 的 `say` 抽取）
- `data/chat/ChatClient.kt`：`POST {baseUrl}/v1/chat/completions` + `stream:true`，手写 SSE 行解析；
  `PromptBuilder` 组装两层角色卡 + 单行 JSON 输出协议
- `data/chat/ConversationStore.kt`：对话历史（SharedPreferences，上限 100 条）
- `AppContainer`：加 `conversation` / `chat` 两个 lazy
- `MainActivity`：`onSend` 走真实请求，流式增量更新字幕，`onDone` 落盘 + 切情绪
- `res/xml/network_security_config.xml` + Manifest `android:networkSecurityConfig`

**三个值得记的实现决策**：
1. **不用 OkHttp `EventSources`**：它绑死了 `data:` 解析与生命周期，而我们需要在
   `onFailure` 里区分「用户连发打断」与「网络断了」。自己读 `readUtf8Line()` 更简单。
2. **字幕边收边解**：模型输出 `{"say":"...","emotion":"..."}`，但流式到达时是半截 JSON。
   等完整再显示会让用户盯着空白；直接显示原文会出现 `{"say":"主` 这种噪音。
   `SayExtractor` 定位 `"say"` 之后一直读到未闭合的引号为止，把已到达的部分当字幕。
3. **历史用 SharedPreferences 不用 Room**：p5 的记忆层要整体重做存储
   （`Message` + FTS4 bigram 影子列 + `Block` 分层摘要），现在上 Room 等于白写迁移。
   这里的数据结构已按 p5 的 `Message` 对齐（role/content/seq），迁移时直接灌进去。

**踩坑 1：CLEARTEXT 被拦**
现象：字幕显示 `网络断了：CLEARTEXT communication to 127.0.0.1 not permitted by network security policy`。
根因：Android 9+ 默认禁明文 HTTP。用户的真实场景（Ollama :11434、one-api、局域网）全是 http，
必须放开。修法：加 `network_security_config.xml` 的 `base-config cleartextTrafficPermitted="true"`
并显式写 `trust-anchors`（比 `usesCleartextTraffic="true"` 更可控，将来按域名收紧只改一份 XML）。
设置页与 README 都提示「公网端点请用 https」。

**踩坑 2：mock 服务器一个 chunk 都发不出去**
`tools/mock_openai.mjs` 里把 `clearInterval` 挂在 `req.on('close')`，
但 Node 16+ 里 `IncomingMessage` 的 `close` 在**请求体读完时**就触发，定时器被立刻清掉。
改成 `res.on('close')` 后正常。

**怎么验证**（真机 + `adb reverse tcp:8080 tcp:8080` + `node tools/mock_openai.mjs`）：
- mock 侧日志：`model=deepseek-chat stream=true messages=3`、`last user: "hello"`
  （→ 证明请求体正确：1 条 system + 1 条 user）
- 界面截图 `.tmp_probe/s4.png`：字幕干净显示 `主人终于来啦，我一直在等你呢。今天想聊点什么？`
  （**没有** `{"say":` 噪音，说明 `SayExtractor` 生效）
- 历史落盘：`run-as ... cat shared_prefs/virtual_companion_chat.xml` →
  `[{"role":"user","content":"hello","seq":1},{"role":"assistant","content":"主人终于来啦…","seq":4}]`
- 情绪：`onDone` 里 `emotion = reply.emotion` + `controller.setEmotion(reply.emotion)`，
  渲染侧 `EMOTIONS` 表已覆盖 happy/sad/angry/shy（`render.html` 第 74–79 行）

**有无偏离**：无。新增一个 `tools/mock_openai.mjs` 测试工具（不入 APK），

## p3 语音唤醒：KWS + 本地 ASR + 唤醒后链路

**做了什么**

**改了哪些文件**

  音频源三级回退 `VOICE_RECOGNITION → VOICE_COMMUNICATION → MIC`。
- `voice/KwsEngine.kt`（新建）：sherpa-onnx `KeywordSpotter`，关键词来自
  `assets/kws/keywords.txt`。所有公开方法 **`@Synchronized`**（见踩坑 2）。
- `voice/LocalAsrEngine.kt`（新建）：sherpa-onnx 流式 zipformer-zh-14M int8，离线兜底。
- `voice/VoiceEngine.kt`（新建）：状态机 `IDLE/AWAKE/THINKING/SPEAKING/ERROR`，

- `voice/AsrBackend.kt`（新建）：ASR 后端接口，p4 的腾讯云 WebSocket 直接实现它，
  换后端不动状态机。
- `voice/KwsSelfTest.kt`（新建）：离线自检，wav 帧喂给 KWS 并打命中/解码统计。
- `MainActivity.kt`：接麦克风权限（`RequestPermission`）、`sendText()` 统一文字与

- `data/SettingsStore.kt`：所有字段统一从根 JSON 读（见踩坑 4）。
- `app/src/main/assets/kws/keywords.txt`（新建）：`x iǎo j īng :2.0 @小鲸`。
- `data/model/AppSettings.kt`：`kwsThreshold` 默认 0.35 → **0.15**。

**踩坑 1：唤醒词阈值 0.35 太高 + 行内 `#阈值` 语法会让整行失效**
现象：真机上怎么说「小鲸」都不唤醒，但引擎日志显示在正常解码。
定位：造 6 个词表变体 × 3 个阈值，跑合成音频矩阵。结果：
- `x iǎo j īng @小鲸`：th=0.35 不中，**th=0.15 命中**，th=0.05 命中
- `x iǎo j īng #0.3 @小鲸`：**0.35/0.15/0.05 全不中**
→ 行内 `#<阈值>` 在本机（sherpa-onnx v2.0.1 + kws 模型 2025-12-20）会让整条关键词
失效；阈值只能从 `KeywordSpotterConfig.keywordsThreshold` 全局设，且必须 ≤0.15。
修法：词表只留 `x iǎo j īng :2.0 @小鲸`，阈值默认值改 0.15。
**追加坑**：改默认值后设备上仍旧不生效，因为 SharedPreferences 里存了旧的
`kwsThreshold:0.35`。必须 `rm shared_prefs/virtual_companion_settings.xml`。

**踩坑 2：`KeywordSpotter` 非线程安全 → SIGSEGV 直接闪退**
现象：注入测试时 App 崩溃。
logcat：`Fatal signal 11 (SIGSEGV) ... in libsherpa-onnx-jni.so`，
栈顶 `Java_com_k2fsa_sherpa_onnx_KeywordSpotter_decode+52` ← `KwsEngine.feed+78`
← `VoiceEngine.onFrame+484`。
根因：麦克风采集线程与注入线程并发调 `decode`。
修法：`KwsEngine` 的 `load/feed/reset/release` 全加 `@Synchronized`，
`VoiceEngine.onFrame` 用 `frameLock` 串行化（原主体拆成 `deliver()`）。
修后 `grep -c "Fatal signal"` = 0。

**踩坑 3：唤醒瞬间同步加载本地 ASR 要 8 秒，首句必丢**
现象：KWS 命中后 `→ AWAKE` 比 `HIT` 晚 **8.04 秒**，随后 `final: ''`。
根因：`enterAwake()` 里同步 `new LocalAsrEngine + load()`，24.5MB onnx 在 MT6761
上冷启动实测 **8127ms**，这 8 秒音频帧全被阻塞丢弃。
修法：`VoiceEngine` 持有唯一的 `localAsr`（`by lazy`），在 `start()` 的后台 IO 里
**预热**（日志 `local asr warmup 8127ms`），`LocalAsrBackend` 只借用不重建。
修后：`HIT` 到 `→ AWAKE` 间隔 **6ms**，首句正常出字。

**踩坑 4：API Key 明明填了却报「还没有填 API Key」**
现象：prefs 文件里 `app_settings.llm.apiKey` 有值，界面却提示没填。
根因：`SettingsStore` 早期把 `llm/tts/wake` 存成**并列的顶层 key**，
与根 JSON（`app_settings`）里的同名嵌套字段各存一份；两处不同步时读到了空的那份。
修法：所有字段统一从根 JSON 读（`private fun root() = AppSettings.fromJson(readJson(KEY_ROOT))`），
顶层 key 只写不读，兼容旧数据。

**踩坑 5：扬声器回放测唤醒根本测不通（物理限制，不是代码 bug）**
现象：`tinyplay` 播「小鲸」，麦克风峰值 0.02–0.13 但 KWS 的 `raw` 始终为空。
根因：`src=6` = `VOICE_RECOGNITION`，该源自带 AEC/NLP，**把自家扬声器的声音当回声消掉**。

**踩坑 1：火山事件号初版全错，三帧抢跑被服务端丢弃**
初版凭记忆写了 StartSession=50 / TaskRequest=51 / FinishSession=52 / TTSEnded=353，
全部错误。抓官方文档 `https://www.volcengine.com/docs/6561/1329505` 逐条核实后修正：

| 事件 | 正确值 | 初版（错） |
|---|---|---|
| FinishConnection | 2 | 53 |
| StartSession | 100 | 50 |
| FinishSession | 102 | 52 |
| SessionFinished | 152 | 151 |
| SessionFailed | 153 | 152 |
| TaskRequest | 200 | 51 |
| TTSEnded | **不存在** | 353 |

协议还有时序硬约束：必须先收到 `ConnectionStarted(50)` 才能发 `StartSession(100)`，
先收到 `SessionStarted(150)` 才能发 `TaskRequest(200)`。初版三帧一口气发，服务端直接不理。
修法：`speak()` 只发 StartSession 并存 `pendingText`，收到 150 后在 `flushTaskRequest()` 里补发 200 + 102。

**踩坑 2：连接级事件的 body 里没有 session_id 段**
现象：`decode ws request failed: unable to decode V1 protocol message:
declared body size does not match actual body size: expected=0 actual=6`。
根因：连接级事件（1/2/50/51/52）的 body 直接是 `uint32 payloadLen + payload`，
没有 `uint32 sidLen + sid`；初版给所有帧都写了 0 长度 sid，服务端把它当成了 payload 长度。
修法：`buildFrame()` 里 `if (event !in CONNECTION_EVENTS) { 写 sidLen + sid }`。
`parseFrame()` 相应改成启发式：长度合理（0..256）且后面还放得下 payload size 才当 id 读，
因为服务端回 ConnectionStarted 时**会**带 36 字节的 connect id。

**踩坑 3：TTS 播完状态卡在「说话中」不动**
现象：截图显示 chip 一直「说话中」，日志有 `SessionFinished` 但没有回到 AWAKE。
根因两处叠加：
1. `TtsPlayer` 播放线程 `queue.poll(60ms) ?: continue` —— 队列排空后永远返回 null，
   死循环，`finally { onIdle?.invoke() }` 永不执行。
2. `VolcanoTtsClient` 收到 `SessionFinished(152)` 只 `countDown()`，**没有通知播放器「没有音频了」**。
修法：`TtsPlayer` 加 `@Volatile inputDone` + `markInputDone()`，播放循环改成
「队列空且 inputDone → break，否则继续等」；`VolcanoTtsClient` 在 152 分支补 `onDone?.invoke()`；
`VolcanoTtsSpeaker` 的 `onDone` 里调 `p.markInputDone()`。

## p5 记忆层：billion-context Phase 1 移植（Room + FTS4 + BM25 + 分层折叠）

**四个真实缺陷（都是真机上量出来的，不是推演）**

1. **FTS4 默认分词器对中文等于不可用**。目标机 sqlite 3.28.0，`simple` 与 `unicode61`
   下 `MATCH '妹妹'` 返回 0 行。`tokenize=icu zh_CN` 能命中但只认整词（单字 `华` 不中）。
   → 自建 bigram 影子列：索引写 `主人 人终 终于 于来…`，查询写 `t1 OR t2 OR …`。
   实测 2000 轮建库 0.26s、单次 3-term OR + matchinfo 查询 1.8ms、进程峰值 8.4MB。
2. **`rank(matchinfo(...))` 在目标机上直接报错**：`Error: wrong number of arguments
   to function rank()`。→ 只从 SQL 取回 matchinfo，在 Kotlin 里手写解析
   （布局 `p / c / n / a[p*c] / l[c] / x[p*c*3]`，每步带边界检查），并顺手把打分函数改名
   避免与内置 `rank` 冲突。
3. **Robertson IDF 在小语料上归零**：`max(log((N-df+0.5)/(df+0.5)), 0)` 在 `df ≥ N/2`
   时恒为 0（实测 N=4/df=2 → 0.0000，那几条记忆再也排不上来）。→ 换 Lucene 变体
   `log(1 + (N-df+0.5)/(df+0.5))`。
4. **纯 BM25 会稳定返回过期事实**（最要命）：5 对「同谓词、不同时间」的记忆 BM25 分数
   完全打平（杭州 365 天 vs 成都 3 天都是 4.3293；后端 400 天 vs 前端 6 天都是 7.4080），
   胜负由 rowid 决定 → **5/5 全部返回最旧那条**，模型会一直说旧地址。
   → 乘时间衰减 `0.6 + 0.4*exp(-age_days/30)`，保留 0.6 下限（只让排序让位，不让旧事实
   搜不到），**5/5 全部纠正**。

**分层折叠：三个自己踩出来的坑**

- `foldOnce` 最初 `take(BLOCK_SPAN)` 没有减去 `keepRecent`：当未折叠消息只比保留窗口多 1 条时，
  会把**含最近消息在内的整批**全部 `dropUpTo`，下一轮 `recent()` 直接返回空，
  模型看不到刚说过的话。修法：`take((live.size - keepRecent).coerceAtMost(BLOCK_SPAN))`。
- `promoteTier` 不筛 `survivedCount`：每轮都拿最早的 4 个块重新并一次，`block` 表里出现
  id 5/7/9 全是 `tier=2, span 1..8` 的重复父块。修法：`.filter { it.survivedCount == 0 }`，
  并把合并规模从 4 改成 `PROMOTE_THRESHOLD=5`（与内核 `survivedCount>=5` 对齐）、加 `MAX_TIER=3` 上限。
- `buildContext` 硬编码 `tier >= 2`：刚折出来的 T1 块既不在 wire 历史里（消息已 `dropped`）
  也不在摘要里，那几条记忆等于凭空消失。修法：改成只注入 `survivedCount == 0` 的**叶子块**，
  这才是内核「原文永不删、只从 wire 移除」的正确读法。

**另外修掉的两个 p5 触发出来的老问题**

- **当前用户消息被发两遍**：`sendText` 先落库再读 `recent()`，读回来的历史里已经含这一条，
  而 `PromptBuilder` 末尾又追加了一次 `userInput`。模型开始抱怨「你是不是复读机坏了呀」。
  → 记住 `append` 返回的 ref，读历史时 `filterNot { it.ref == currentRef }`。
- **折叠触发只看条数不看体积**（用户 m03369 提的）：加了 `contextWindow`（token）配置 +
  `TokenEstimator`（CJK 按 1 字符 1 token 保守高估，其余 4 字符 1 token），
  `buildMessages` 按预算从新到旧挑历史，折叠触发改成「条数超窗口 或 token 超预算 60%」。
  两个条件并存：只看条数会在长消息场景顶爆窗口；只看 token 则窗口调到 1M 后永远不折叠。

**还有一个流式解析的真 bug（思考等级打开后必然出现）**

## p5-7 拆分记忆边界与成本守卫，折叠改为循环

用户连续追问（m03994 / m04004 / m04015 / m04027 / m04031），最后拍板（m04034）：
`改，入口放到到开发这个设置里面去，正常按默认来`

### 为什么改
原来只有一个 `historyWindow`，同时承担三种职责：
1. 请求带几条历史 —— `data/chat/ChatClient.kt` 的 `buildMessages` 里 `history.takeLast(window)`；
2. 折叠保留窗口 —— `MemoryStore.foldOnce(keepRecent = historyWindow)`；
3. 检索深度 —— `MainActivity` 里 `memory.recent(historyWindow + 1)`。

改一个数会同时动三处，用户调「记得久一点」时会连带把请求变大、把折叠窗口改宽，
反之亦然。对话里出现了「历史条数上限到底是什么」的连续追问，本质是这个耦合不可解释。

另外自查发现两个真缺陷：
- token 阈值触发时 `foldOnce` 只折 `BLOCK_SPAN` 条（8），但如果剩余条数只比 keep 多 2~3 条，
  就会折出 2~3 条的碎块，5 个碎块才够晋升一级，T1→T2 的压缩率不可控；
- `dropUpTo` 只把 `message.dropped` 置真、不删 `message_fts` 行，
  导致同一条旧消息既出现在「更早的对话摘要」里、又出现在「相关旧记忆」里。

## p5-8 billion-context 内核整体移植（替换自研记忆层）

### 为什么改
p5 的自研记忆层是「手抄内核能力 + Kotlin 拼装」的混合路线，实测有两处硬伤：
1. 摘要用 `batch.joinToString("；") { it.text.take(60) }` 本地拼接，没有任何长度目标，
   实测保留率 **115%**（摘要比原文还长），等于把原文换个字段存一遍；
2. `buildContext` 按 `startRef` 升序取块，先用最旧的块把 700 字预算占满，
   最新的块被静默丢弃 —— 越近的记忆越进不来，方向反了。
用户在 m04254/m04277 明确要求「精简后整体移植」「尽量减少拼接」，
m04513 三项决定：①整体 vendor 内核、删自研实现；②压缩时调模型写摘要；③按内核默认行为。

### 做了什么
**vendor 内核（`app/src/main/assets/kernel/`）**
- `index.js` 321235 B / `chunk-MXL3G3BN.js` 1991 B / `chunk-Q3P5Z2PV.js` 27127 B —— 内核原样拷贝，
  只把 4 条 Node 内置 import（`crypto`/`fs`/`path`×2/`module`）改成 `./shim-node.js`；
- `shim-node.js` 1250 B —— 浏览器安全替身：`createHash` 退化成 FNV-1a（只服务 CCR 哈希，
  该功能默认关闭）、`readFileSync` 抛错、`readdirSync` 返回空数组、`join/resolve/dirname/basename/isAbsolute` 纯字符串实现；
- `vc-memory.js` —— 唯一接缝（宿主适配层），把所有内核调用收进一个文件，Kotlin 只调它；
- `host.html` —— 不可见 WebView 宿主页，动态 `import('./vc-memory.js')`。

**Kotlin 侧**
- 新增 `data/memory/KernelMemory.kt`（430 行）：WebView + `addJavascriptInterface` 桥，
  把 `turn/apply/project/search/compressPrompt/status/exportState/importState` 封装成 suspend 函数；
- 新增 `data/memory/MemorySummarizer.kt`（149 行）：把内核 `compressPrompt()` 的原文当 system、
  区间原文当 user，让模型输出 `{"summary":"...","topic":"..."}`；
- 重写 `MemoryEntities.kt`（只剩 `Message`/`AcpRule`/`KvEntry`）、`MemoryDao.kt`、`MemoryDatabase.kt`（version 2）；
- **删除** `Bm25Scorer.kt`/`CjkTokenizer.kt`/`MemoryStore.kt`（约 517 行自研记忆代码）；
- `ChatClient.kt` 新增 `complete()`（非流式，供摘要调用）；
- `MainActivity.kt`：`persistAssistant` 改为「落库 → turn → 若 shouldInject 则 summarize → apply」。

### 踩到并修掉的 6 个真缺陷
1. **`CoreMessage` 字段名是 `text` 不是 `content`**。传 `content` → 内核读到 `text` 为 undefined
   → token 全 0 → `compressibleRanges` 永远为空，**没有任何报错**，只表现为「永不压缩」。
2. **`applyCompression` 返回 `{state, result}` 不是 `state`**。取错字段表现为「apply 无报错但 blocks 一直是 0」。
3. **`renderTags:"text-only"` 会把 `<acp tokens=...>m00175</acp>` 插进消息正文**，手机 UI 上是乱码 → 必须用 `"none"`。
4. **WebView 被反复重建**：`ensureStarted()` → `restore()` → `call()` → `ensureStarted()` 递归，
   logcat 里 `kernel ready methods=9` 每秒刷几十条。拆成 `ensureStarted()`（只建 + 等 boot + restore）
   与 `invokeKernel()`（不再 ensure）后，只剩一条 `restored messages=4 state=594B`。
5. **摘要保留率 115%**：prompt 只给上限（3000 字）不给目标，模型写满。
   按论文实测的 1/8 保留率改成 `targetChars = srcTok / SUMMARY_DIVISOR(8)`，
   并在 prompt 里写「这是目标不是上限」，另加 `clipAtSentence()` 在句末断开做硬裁。
   修后摘要 48–74 字，压缩比 45–50%。
6. **压缩率显示 121% 是假象**：Kotlin 侧用 `TokenEstimator`（含 `PER_MESSAGE_OVERHEAD=4`）
   算 wire，而 `turn.tokens` 是 JS 侧 `defaultCountTokens`，两把尺子混用。
   修法：`vc-memory.js` 的 `turn()/apply()` 增加 `wireTokens`（用内核同一把尺），Kotlin 改读它。
   修后未压缩阶段显示 100%（正确）。

### 关键决策：工作集 ≠ 模型真实窗口
内核的三门合取（usage ≥ 百分比 且 增长 ≥ 绝对值 且 区间 ≥ 最小值）都是按 1M 窗口设计的默认值：
`growthFloor=50000` token、`minCompressRange=5000` 字符、`tier2Trigger=1000` 个 T1 块。
伴侣对话一整天也就 2–4K token，**用默认值永远不触发**（真机连发 11 轮 inject 恒为 false，
`usage=345/1048576=0.0003`）。

解法是引入「工作集」概念：`KernelMemory.workingSet(contextWindow, maxTokens)` 取
`min(usable, 6000)` 且不低于 2000，作为 `defaultConfig()` 的窗口参数传给内核；
再由 `vc-memory.js` 的 `MOBILE` 只收缩**绝对门槛**（`growthFloor:300 / growthCap:600 /
minGrowthFloor:180 / minCompressRange:250 / preserveRecentMessages:4 / preserveRecentTokens:500 /
tier2Trigger:4 / tier3Trigger:8`），**百分比一律保持内核默认 0.75/0.45/0.95**。
Node 侧扫测对比：保留默认百分比 + 只缩放绝对门槛 → t160 收敛 61.5%；
把 `maxContextLimitPct` 压到 0.5 → 71.5%，反而更差。

### 怎么验证
**离线（Node，`C:/Users/<you>/AppData/Local/Temp/kerneltest/v2/t13–t23.mjs`）**

## p6 联调验收：修复三个致命链路缺陷与记忆注入断链

### 为什么做这一步
p5-8 把内核搬进来后，单元层面都通了，但**端到端跑一遍才发现若干「各自正常、连起来不通」的缺陷**。
本步的目标只有一个：真机上从「喊小鲸」到「它答得上来」整条链路无断点，
并且**用可观测证据证明记忆真的生效**，而不是靠上下文窗口。

### 做了什么

**1. 腾讯云 ASR 响应结构读错（决定性缺陷）**

症状：能唤醒、`TencentAsr: connected` 日志出现，但一条 partial/final 都没有，
`AWAKE` 后 8.03 秒静默超时退出。

原实现假设响应形如 `{"slice_type":1,"result":[{"voice_text_str":"..."}]}`，
实际是（`x` 为真实的腾讯服务响应，用 `.tmp_probe/tc_probe.py` 独立验证）：

```json
{"code":0,"result":{"slice_type":1,"voice_text_str":"小晶今天天气怎么样", ...}}
```

两处错位：
- `slice_type` 在 `result` **里面**，不在顶层 → 原代码 `o.optInt("slice_type")` 恒为 0；
- 文本是 `result.voice_text_str` 这个**字符串**（累计整句），不是 `result` 数组 → `optJSONArray("result")` 恒为 null。

结果所有识别结果都被 `if (piece.isNotBlank())` 静默丢弃，一条日志都不留。

修法（`voice/TencentAsrBackend.kt` 的 `onMessage`）：先取 `result` 对象，
再判 `has("voice_text_str")`，有则 `onPartial`，`slice_type == 2` 则 `onFinal`；
`final:1` 的收尾包则补发最终文本。

**2. 云端 ASR 后端从未绑定回调**

`MainActivity` 里 `voice.cloudAsrFactory = { TencentAsrBackend(settings.tencentAsr) }`
只是 new 出实例，云端后端的 `onPartial/onFinal/onError` 全是 null。
本地后端因为是同一个类里的内部类，构造时就绑好了，所以只有云端受影响。

修法（`voice/VoiceEngine.kt`）：抽 `bindCallbacks(b)`，
在 `openBackend()` 里把后端塞进 `backend` 之前统一绑定。

**3. `endSpeaking()` 不重开麦克风（用户报「第一轮正常，第二轮无法唤醒」）**

`beginSpeaking()` 里 `capture.stop()` 关麦防自唤醒，但 `endSpeaking()` 只调 `openBackend()`，
**从没把麦克风打开**。于是 TTS 播完之后麦克风一直是关的，
第二轮喊「小鲸」收不到任何音频，8 秒后静默退出；
连诊断日志 `mic frames=...` 也停了，极易误判成 KWS 坏了。

修法（`voice/VoiceEngine.kt` 的 `endSpeaking`）：重开采集前先 `kws.reset()`，
否则上一轮残留的音帧会把下一轮的词切碎；然后 `capture.start(...)`，再 `openBackend()`。

**4. 折叠摘要从未进入 prompt（最严重）**

`ChatClient.buildMessages` 只接收 `history`（user/assistant），
而内核 `prune` 投影出的摘要消息 `role` 是 `system`，正文以
`[Compressed conversation section]` 开头。`sendText` 里这一行把它们全扔了：

```kotlin
.filter { it.role == "user" || it.role == "assistant" }
```

真机 `MemWire` 全量转储证据（修复前）：`wire` 一共 11 条，
其中 10 条是摘要，**一条都没进 prompt**，`ctx 0字`。

修法（`MainActivity.kt`）：把 `wire` 里的 `system` 消息单独取出来，
拼成 `【更早的对话摘要】` 段落并入 `memoryCtx`。修后 `ctx 0字 → 1059字`。

**5. 摘要只描述过程、不含事实**

旧摘要：「主人连发第4-6轮相同消息（加班到十点、买冰美式、周末约西湖、让早点休息）；

修法（`MemorySummarizer.kt` 的 prompt）新增一节「摘要必须能直接回答追问」：
要求写成**事实本身**、每句自带主语、专有名词原样保留、

**6. 摘要被整串 JSON 污染**

- `MemorySummarizer.parse()` 新增 `salvageSummary()`，从残缺文本里逐字符抢救
  `"summary": "..."` 的值；救不出来就返回 null（宁可不压也不存脏数据）；
- `vc-memory.js` 新增 `sanitizeBlocks()`，在 `importState()` 时清洗**已落盘的**脏块
  （老数据不会因为改了代码就自愈）。

## p6-1 修复「切后台再回来就再也唤不醒」

### 现象（用户报告）
> 现在无法对其进行唤醒。将状态初始化。

真机状态：进程活着（pid 存在）、麦克风权限已授予、屏幕亮着，
但 logcat 停在 `VoiceEngine: → IDLE (endSpeaking but idle)`，之后**再没有任何采集日志**。
喊唤醒词毫无反应，只能杀进程重开。

### 根因（两个缺陷叠加，缺一不可）

**缺陷 A：回到前台从不重新 `start()`**

`MainActivity` 里引擎只在下面这个 `LaunchedEffect` 内启动：

```kotlin
LaunchedEffect(micGranted, settings.wake, settings.asrEngine) {
    if (micGranted && !voiceStarted) { voice.start(); voiceStarted = true }
}
```

`ON_STOP` 时 `voice.stop()` 并把 `voiceStarted = false`，
但 `micGranted / settings.wake / settings.asrEngine` 三个 key 一个都没变，
**`LaunchedEffect` 不会重跑** → 回到前台后 `running` 永远是 false。

**缺陷 B：`endSpeaking()` 的死路分支不重开麦克风**

```kotlin
if (!awake) {
    enterIdle("endSpeaking but idle")
    return          // 麦克风已被 beginSpeaking() 关掉，这里直接返回
}
```

麦关着、`awake` 是 false、`running` 是 true。
`start()` 里又有 `if (running) return` → 连手动点麦克风也救不回来。

两个缺陷分开看都不致命，叠在一起就是**永久卡死**。

### 修法（四处）

1. **`VoiceEngine` 抽出 `reopenMicIfNeeded()`**：重开前先 `kws.reset()`，
   否则停采期间残留的音帧会把下一轮的词切碎。三处调用：`endSpeaking` / `start` / 看门狗。
2. **`endSpeaking` 调整顺序**：**先开麦，再判断 `awake`**。
   原来顺序反了才走进死路。
3. **`VoiceEngine.start()`**：`running` 为 true 时不再无脑 `return`，
   而是先尝试 `reopenMicIfNeeded()` —— 让「再点一次麦克风」成为有效的恢复手段。
4. **`MainActivity` 加 `ON_START` 分支**：`micGranted && !voiceStarted` 时重新 `voice.start()`。

### 顺带修掉一个我自己引入的竞态

加看门狗后真机出现**两次** `AudioCapture: started`：

```
17:35:48 W VoiceEngine: watchdog: mic is dead while IDLE, reopening
17:35:50 I AudioCapture: started ...      ← start() 建的
17:35:51 I AudioCapture: started ...      ← 看门狗建的
```

看门狗（主线程）与 `start()`（IO 线程）几乎同时进入 `AudioCapture.start()`，
两边都读到 `running == false`，各建一个 `AudioRecord`，两个采集线程抢麦克风。

修法：
- `AudioCapture.start()/stop()` 加 `@Synchronized`；
- 看门狗增加 `if (!_ui.value.ready) return`（`ready` 在 `start()` 全部做完后才置 true）。

### 怎么验证

**切后台再回前台**
```

AudioCapture: started → VoiceEngine: started wake=true        ← 回前台自动重开
mic frames=216 peakRms=0.14 src=6 decodes=1                   ← 确实在采
```

**只看一次采集（竞态已消）**
```

I AudioCapture: started source=VOICE_RECOGNITION     ← 只有这一条
I VoiceEngine: started wake=true asr=CLOUD_TENCENT
```

**整链路（注入唤醒词 WAV）**
```

I VoiceEngine: → AWAKE (kws:小鲸)
```

**连跑 3 轮不重启**：每轮都是 `SPEAKING → mic back on → AWAKE`，
第 3 轮结束停在 `IDLE (endSpeaking but idle)`（因为中途 `manual stop`），
**但麦克风仍是开的**，重启后立刻 `HIT → AWAKE` 验证通过。

## p6-3 唤醒词热切换、离线 ASR 修正、分组保存与背景降噪

### 为什么改（用户报的四个问题）

| 原话 | 现象 |
|---|---|
| `在设置页更换唤醒词实际是不生效的，依旧只有旧唤醒词可唤醒` | 日志 `wakeWord=小爱`，实际只有「小鲸」能唤醒 |
| `离线ASR好像也是不成功的` | 本地识别每句都是与音频无关的胡话（「又开始显示无想硬了」），且永不 endpoint |
| `你可以每一个项目下面多一个保存按钮。在修改了配置后会出现` | 设置项改完即写盘，无法「改一半先不生效」 |
| `我这边有背景说话杂音，你记得注意一下` | 背景说话被当成用户输入，且静默计时被无限续命、退不回待机 |

### 做了什么

**1. 唤醒词真正热切换（三个真缺陷叠加）**

- `KwsEngine` 的关键词是编译期固定 assets（`kws/keywords.txt` 内容 `x iǎo j īng :2.0 @小鲸`），`CharacterCard.wakeWord` 只喂给了状态 chip 的那行文案。
- 新增 `app/src/main/assets/kws/pinyin.tsv`（**20924 字 / 210603 B**，格式 `字	initial final`），由 `.tmp_probe/gen_pinyin.py` + `pypinyin` 生成，只保留声母与韵母都在 `kws/tokens.txt`（263 行）里出现的字 —— 保证拼出来的行模型一定认得。
- `KwsEngine.setWakeWord(word, boost)`：`toPinyin` 逐字查表 → 拼 `"$py :$boost @$clean"` → `KeywordSpotter.createStream(line)` 换流。`javap` 确认 `createStream(String)` 存在，**换词不必重建 5.4MB 模型**。
- **真缺陷 A**：`VoiceEngine.prepareWakeWord()` 原本直接赋 `kws.wakeWord = word`，而 `start()` 的守卫是 `if (kws.wakeWord != pendingWakeWord) setWakeWord(...)` —— 两值已相等，换词逻辑被跳过，`keywordsLine` 永远是空，`load()` 退回 assets 默认词。改成调 `kws.setWakeWord(...)` 无条件写入。
- **真缺陷 B（ANR 元凶）**：`KwsEngine.setWakeWord` 是 `@Synchronized` 的，冷启动时和 IO 线程上的 `load()`（5 秒）抢同一把锁；而它从 Main 的 `LaunchedEffect` 里调 → `Input event dispatching timed out ... Waited 5005ms for FocusEvent` → 「应用无响应」。改成：主线程只做不碰模型的 `toPinyin` 校验，真正的换流丢到 IO。

**2. 离线 ASR 修正（两个真缺陷）**

- **缺陷 C：stream 复用**。`beginUtterance()` 原来只对同一个 `OnlineStream` 调 `reset()`，但 `finish()` 里调过 `inputFinished()`，流被标记「输入结束」后再 `acceptWaveform` 会解出乱码。改成每句 `stream?.release()` + `createStream()` 新建（stream 轻、模型重）。
- **缺陷 D：跳帧**（我在降噪时引入的）。本地 zipformer 是**连续特征流**模型，静音段整帧丢弃会把声学特征切碎 —— 表现就是「又开始显示无想硬了」这种碎片。修法：给 `AsrBackend` 加 `needsContinuousAudio`（本地 true、云端 false），`deliver()` 里 `if (!speech && !hangover && !(backend?.needsContinuousAudio ?: false)) return`。
- 顺带把 `LocalAsrEngine` 的 `load/beginUtterance/feed/finish/release` 全加 `@Synchronized` —— 否则预热协程与 `openBackend()` 可能并发 `load()`，各建一个 recognizer 互相踩。
- 修后真机：`HIT keyword=小鲸 → → AWAKE → final: '我住在杭州做后端开发' → TaskRequest chars=32 → playback idle → AWAKE (tts done)`。

**3. 背景说话降噪（三层，全部不碰 KWS 喂帧）**

前提：KWS 是流式的，为省电/防误触发而跳帧会让主人自己也唤醒不了（踩过）。所以防护放在「命中后复核」和「送 ASR 的帧」两处。

- **命中复核**：环形缓冲 10 秒（100 帧）取 **20 分位**当噪声底（均值会被说话拉高），`noiseFloor` 0.95/0.05 平滑跟随；命中后要求最近 1 秒峰值 `recentPeakRms(20) >= MIN_SPEECH_RMS(0.010)`，否则丢弃并计 `noiseGuardDrops`。**必须用峰值不是当前帧**：KWS 解码有延迟，命中往往在音节结束后 1–3 帧才报，那一帧可能已是静音（实测被误拒过）。
- **静默计时改由能量驱动**：`onPartial` 不再 `armSilenceTimer()`。原来背景说话不断产生 partial，每来一次就重置 8 秒计时，会话永不结束、麦克风常开。
- **静音段不送云端**：`if (!speech && !hangover(500ms)) return`，省流量、少一次把背景噪声识别成文字的机会。
- **会话硬上限**：`WakeConfig.maxAwakeMs = 60_000L` + `armAwakeCap()`，到点无论有没有人说话都退出，防「背景一直聊天」无限延长。

**4. 设置页分组保存（快照比较，不写 30 多处 dirty 标记）**

- `Section(title, summary, defaultExpanded, snapshot: Any? = null, onSave: (() -> Unit)? = null, content)`。设置是整块 data class、每次改动产生新实例，`!=` 天然就是「改过」；逐字段标记要写 30 多处，漏一个就永远不出按钮。
- `val dirty = snapshot != null && baseline != snapshot`；展开区底部 `if (dirty) PillButton("保存本组")` else 保存后显示「已保存」。
- **踩坑**：不能在 composable 体里直接 `if (dirty) expanded = true`（重组期间改状态），要用 `LaunchedEffect(dirty){...}` 并配 `wasDirty` 边沿检测。
- 保存「角色卡 / 唤醒」时调 `voice.setWakeWord`，失败提示「唤醒词「$w」里有模型不认识的字，换一个吧」；保存「语音」时重新 `voice.configure(...)`。

## p6-4 让「离线 / 在线语音切换」可被验证

**为什么改**

用户问：「那你怎么确定离线语音和在线语音切换成功了。」
自查后发现两个真实缺口，光靠日志糊不过去：

1. **`cloudFailed` 是永不复位的粘滞位**。`VoiceEngine.openBackend()` 里 `wantCloud = preferredEngine == CLOUD_TENCENT && !cloudFailed`，
   而 `configure()` 只改 `preferredEngine`，不复位 `cloudFailed`。后果：云端失败一次 → 降级本地 → 用户在设置里切回「云端」→ **仍然走本地，且无任何提示**。
   这个粘滞位本身是为了避免每句话都重连失败的云端拖慢响应，不能让「切回云端」失效。
2. **`asrLabel` 从来没显示在任何地方**。`grep -rn "asrLabel"` 除了 `VoiceEngine.kt` 之外 0 处命中 ——

## p6-7 修正设备侧记忆窗口，并修掉两个启动期并发缺陷

**用户指令**：`你帮我改吧，顺便看看有没有新的bug。`

### 二、新发现的 bug 1：`KwsEngine` 一把锁导致的 6 秒阻塞

**日志证据**（冷启动时）：

```
W irtualcompanio: Long monitor contention with owner DefaultDispatcher-worker-3 (7755)
  at boolean ...KwsEngine.load(float, float, java.lang.String)(KwsEngine.kt:164)
  waiters=0 in boolean ...KwsEngine.setWakeWord(java.lang.String, float) for 6.050s
E VoiceEngine: capture error: AudioRecord 初始化失败：state=0 source=1
```

**根因**：`KwsEngine` 所有方法都用同一个 `@Synchronized`（类实例锁）。
`load()` 要在锁里解析 5.4MB 的 onnx（4–6 秒），这期间 `setWakeWord()` 只能干等 6.05 秒；
紧接着 `capture.start()` 报 `state=0`，三个音源全开不起来，唤醒彻底失效。

**修法**：拆成两把锁，加锁顺序恒为 `loadLock → decodeLock`（无环）：
- `loadLock` 只管模型的建/毁（`load` / `release`）；
- `decodeLock` 既管 `decode`（`KeywordSpotter` 内部非线程安全，并发 decode 会 SIGSEGV），
  也管 stream 的换入换出与释放。
- `spotter` / `stream` / `wakeWord` 加 `@Volatile`；`setWakeWord` 去掉 `@Synchronized`，
  模型还没建好时只记下 `keywordsLine` 并立即返回，由 `load()` 稍后读它建流
  （所以「先改词、后加载」也生效）。
- Kotlin 细节：`fun f(): T = synchronized(lock) { ... }` 里不能出现 `return`（表达式体禁 return），
  所以拆出 `loadLocked()` / `feedLocked()` 两个私有实现，公开方法只做 `synchronized` 包装。
  第一版直接把 `return` 塞进表达式体，编译报 `Missing return statement`。

### 三、新发现的 bug 2：`start()` 重入把麦克风开两次

`running = true` 是**同步**置的，但真正开麦在后台协程里（要先等 4–6 秒的模型）。
这段时间内若再来一次 `start()`（`ON_START` 与 `LaunchedEffect` 同时触发，或用户连点麦克风），
`if (running)` 分支会走 `reopenMicIfNeeded()` 先开一个 `AudioRecord`，
随后第一个协程加载完模型又开一个 → 两个 `AudioRecord` 抢同一路麦克风，
正是上面那条 `AudioRecord 初始化失败：state=0 source=1` 的直接来源。

**修法**：加 `@Volatile private var starting`，`start()` 里 `if (running) { if (starting) return; ... }`；
置位在 `running = true` 之后，三条出口（kws 失败 / capture 失败 / 正常完成）全部复位。

### 四、我自己引入又修掉的 bug 3：换流时的 use-after-free

拆锁后第一版里 `feed` 走 `decodeLock`、换流走另一把锁，看似无关，
但 `setWakeWord` 里的 `old.release()` 会释放 decode 线程正在使用的 `OnlineStream`。
先 free 再 decode 就是 use-after-free，历史表现正是
`Fatal signal 11 (SIGSEGV) ... Java_com_k2fsa_sherpa_onnx_KeywordSpotter_decode`。

**修法**：换流 + 释放旧流整段放进 `decodeLock`，保证没有 in-flight decode；删掉 `streamLock`。

## p6-8 停止时不再释放模型（第四个并发缺陷）

```
19:44:17.006  W Long monitor contention with owner DefaultDispatcher-worker-2 (8896)

                waiters=0 in void ...KwsEngine.release() for 4.305s
19:44:17.030  AudioCapture: started
```

## p6-9 说完话不自动停、消息丢失

**用户报障**：`现在有问题，有时候我说完话过后，他不会自动暂停，会直接等到超时，然后直接这条消息就没了`

**根因（三处叠加）**
1. `TencentAsrBackend` 没有覆盖 `needsContinuousAudio`（默认 false），`VoiceEngine.deliver()`
   把人声之后的静音帧全裁掉。腾讯云 v2 是**服务端 VAD** 判句末（`needvad=1`），
   它必须真的收到那段静音才会吐 `slice_type=2` —— 收不到就永远没有 final。
2. 8 秒静默到点 → `enterIdle("silence timeout")` → 里面 `backend?.close()` 并把
   `partialText` 清空 → 已经识别出来的半句被丢弃，用户看到的就是「消息没了」。
3. `enterIdle` 里不能直接调 `backend.finish()`（本地是同步 onnx 解码数秒，
   而 `enterIdle` 由 Main 调度器的协程调用，会 ANR）。

**修法**
- `TencentAsrBackend.needsContinuousAudio = true`：唤醒态整段音频连续上送，
  服务端 VAD 能听到句末静音。代价 32KB/s，受 `maxAwakeMs`（60s）约束，单次 ≤1.9MB。
- `VoiceEngine.armEndpoint()`：最后一次人声后 `ENDPOINT_MS=900ms` 主动 `finish()`
  （云端发 `{"type":"end"}`，本地触发解码收尾），不依赖服务端 VAD。
- `VoiceEngine.startStabilityWatch()`：识别文本 `TEXT_STABLE_MS=900ms` 不再增长即收尾
  —— 这是对 sherpa「末尾 blank token 时长」判据的近似，与环境噪声无关。
- `enterIdle(reason, flushPending = true)`：若已有半句且尚未 final，**先发出去**再退出；
  `manual stop` / `abort()` 传 false（用户主动打断不该补发）。

## p6-10 换成神经 VAD（不再用能量阈值）

**用户要求**：`不要只考虑风扇，他今后可能会运行在其他环境，去github或网上其他地方找方案。`

**为什么能量阈值不可靠**（不只是风扇）
- 稳态噪声（风扇/空调）：能量恒定，容易被判成「一直在说话」，静默计时被无限续命；
- 瞬态噪声（键盘/关门）：单帧能量可超过轻声说话；
- 机型增益差异：同一句话在不同手机上 RMS 差 3–10 倍，`2.5 倍底噪`这种常数没有普适性。

**业界做法**：逐帧二分类的神经 VAD（WebRTC VAD / Silero VAD / TEN-VAD），判「波形像不像人声」
而不是「有多响」。sherpa 官方端点文档也明确：端点判据应来自**解码回溯路径末尾 blank token 的时长**，
而不是音频能量（`https://k2-fsa.github.io/sherpa/python/streaming_asr/endpointing.html`）。

**落地（不新增依赖）**：`com.k2fsa.sherpa.onnx.Vad` 就在已打包的 AAR 里（`javap` 核实
`Vad` / `VadModelConfig` / `SileroVadModelConfig` 三个类）。新增 `voice/VadGate.kt`：
- `SileroVadModelConfig(model="vad/silero_vad.onnx", threshold=0.5, minSilenceDuration=0.55, minSpeechDuration=0.20, windowSize=512)`
- 内部按 512 样本（32ms）攒帧喂 `vad.acceptWaveform`，`isSpeechDetected()` 作为 speech 判决；
- `vad.empty()` 时 `pop()`，避免语音段缓冲无限增长。

**模型获取（GitHub release 被墙）**：`release-assets.githubusercontent.com` 连不上
（`curl: (7) Failed to connect ... after 6 ms`）；`ghfast.top` 403、`gh-proxy.com` 000。
最终从 HF 镜像拿：`https://hf-mirror.com/deepghs/silero-vad-onnx/resolve/main/silero_vad.onnx`
→ **2,327,524 B**，放在 `app/src/main/assets/vad/silero_vad.onnx`。

**过程中自己引入并修掉的回归**：换成 VAD 之后 `updateNoiseAndDetectSpeech` 不再被调用，
而 `recentPeakRms(20)` 的环形缓冲正是在那个函数里维护的 → 唤醒能量复核读到 0.0 →
每一次真实唤醒都被拒（真机 `kws hit '小鲸' rejected: peak=0.0 < 0.01 (drops=1)`）。
修法：拆出 `trackNoise(rms)` **无条件每帧**维护环形缓冲与底噪，VAD 只负责判决。

**真机验证**：`VadGate: loaded vad/silero_vad.onnx threshold=0.5 minSilence=0.55s`
→ `HIT keyword=小鲸` → `→ AWAKE (kws:小鲸)` → `backend installed: TencentAsrBackend preBuffer=33`
→ `final: '住在杭州，做后端开发。'`（0.25s）→ `→ THINKING` → `→ SPEAKING (mic off)`
→ `→ AWAKE (tts done)`。APK 99,529,686 B；TOTAL PSS 224,782 KB。

## p6-11 说完判定：不再被句中停顿切断，也不再喂风扇噪声

**用户报的现象**（真机，室内唯一噪声是风扇）

1. `有时候我说完话过后，他不会自动暂停，会直接等到超时，然后直接这条消息就没了`
2. `第二条，我说完话就直接发出去了`（测「说完停 2 秒再接着说」，期望合并成一句）

**第一条的根因**（p6-9 已修）：腾讯云 v2 靠服务端 VAD 判句末，但 `VoiceEngine.deliver()`
把人声后的静音帧全裁掉了，服务端听不到句末；8 秒静默一到 `enterIdle` 又把半句清了。
修法：`needsContinuousAudio` 让静音也送 + 自己算端点 + 退出前兜底冲刷。

**第二条的根因（本次）**：`ENDPOINT_MS` / `TEXT_STABLE_MS` 都是写死 900ms。
真人换气、想词的停顿常在 1–2 秒，900ms 必然切开。而且这两条判据是**本地计时器**，
它们会跟服务端的 VAD 抢着报时——日志里 `text stable 1800ms → 主动收尾` 比
`TencentAsr: final` **早 123ms**，差一点就自己把整句切了。

**改动**

1. **「说完判定」变成可调设置**：`WakeConfig.endpointMs`，默认 1500ms，范围 800–2400，
   设置页「唤醒」组新增滑杆。同时它也是腾讯云 query 里的 `vad_silence_time`
   （官方范围 240–2000），两端必须一致——只调本地的话服务端还是按它自己的节奏收尾。
2. **修正 query 字典序**：`vad_silence_time` 必须排在 `voice_format` 之前
   （`vad` < `voi`），否则签名原文错位 → 服务端 4013。实测 `open url=...vad_silence_time=1800&voice_format=1` 之后 `connected` 正常。
3. **本地计时器不再替服务端做决定**：`AsrBackend.hasServerEndpoint`（腾讯云 = true），
   只有「自己不会判句末」的后端（本地 zipformer）才启 `startStabilityWatch()`。
   **这个判断必须放在 `openBackend()` 装好后端之后**——`enterAwake` 那一刻 backend 还是
   null，判出来永远是「没有服务端端点」，实测就因此白跑了一轮。
4. **宽限合并**：final 不再立刻发给 LLM，先挂 `pendingText` 等 `graceMs`
   （句子以 `，、；…` 结尾或 ≤3 字 → 等 `endpointMs`，否则等 `endpointMs/3`）。
   宽限内又出新 partial → 取消宽限、重开后端（服务端 final 后会关会话），
   把两段拼一起；3 秒没有新内容就按续说超时把挂起的句子发出去。
   **判据必须是文字不是能量**：第一版用「一帧 speech 就取消宽限」，
   实测 final 后紧跟一帧 `speech=true`（尾音/AEC 残留），整句被挂起来再也发不出去
   （`继续说 → 取消宽限，已挂起 '住在杭州，做后端开发。'`，之后无下文）。
5. **云端不再送静音**（`needsContinuousAudio` 改回 false）。真机实测证明
   「服务端要听静音才会吐 slice_type=2」是错的：把 `vad_silence_time` 顶到 1800ms
   等 10 秒也没等到，真正的句末一直是我们 `{"type":"end"}` 逼出来的；
   而连续送静音等于把风扇喂给识别器，十秒噪声被解成
   `I will back see that fire my what's the?` 并混进正文。
6. **噪声幻觉尾巴清理**（`stripNoiseTail`）：已出现过中文句末标点就砍掉后面连续的非中文内容
   （尾部无汉字且最长字母串 ≥2）；整句一个汉字都没有则整句丢弃。
   真机对照：修前 `住在杭州，做后端开发。I will back see that fire my what's the?`，
   修后 `住在杭州，做后端开发。`。
7. **底噪估计**：跳过 <0.004 的帧（麦克风被关掉的假静音）+ 改用 20 分位。
   修前 `floor` 被拉到 `1.0E-4`，风扇 0.047 的能量看上去是底噪的 470 倍，
   「比底噪高」判据完全失效；修后 `floor` 稳定在 0.022–0.028。
8. **VAD 与能量联合判决**：`speech = silero && rms >= 0.012 && rms >= floor*2.5`。
   神经 VAD 只答「像不像人声」，挡不住风扇这类稳态强噪声。

**真机验证**：`endpoint 1900ms 无人声 → 主动收尾` → `TencentAsr: final: '在杭州做后端开发。'`
→ `grace 500ms 到期，交给 LLM` → `→ THINKING` → `→ SPEAKING (mic off)`。
说完到开始回应约 **2.4 秒**（判定 1500+400，宽限 500）。APK 99,683,422 B。

**留给用户真机确认的三件事**（注入测试测不出来：注入间隙的假静音会污染底噪估计）
- 正常说一句 → 应该识别完整、不夹英文；
- 说完停 2 秒再接着说 → 期望合并成一句（判定调到 1.8 秒以上更稳）；
- 只开风扇不说话 → 不应该有任何 "final" 冒出来。

## p6-12 识别不全：恢复连续送音频，端点改由识别文本驱动

### 一句结论
「识别不全」不是模型或网络问题，是**我们把一半真实语音当成静音扔掉了**。

### 证据
用户 m06975 报「识别精度没有刚才高了，很容易出现识别不全」后，翻 `gate frames` 日志：

```
20:19:31  gate frames=21 speechOn=5   rms=0.0997 floor=0.0096
20:19:33  gate frames=21 speechOn=0   rms=0.2094 floor=0.0102   ← 响声 0.209 却零帧判成人声
20:19:38  gate frames=20 speechOn=15  rms=... floor=...
```

`speechOn` 是每 21 帧里被判成「人声」的帧数。真人在说话时只判出 1/4 到 3/4，
第三行更是整车响声 0.209（比底噪高 20 倍）却**一帧都没判成语音**。

而 p6-11 我把 `TencentAsrBackend.needsContinuousAudio` 改成了 `false`
（理由是「别把风扇噪声喂给识别器」），于是被判成静音的帧**在 `deliver()` 里就 return 了**，
云端根本收不到 —— 语音被切成碎片，尾字丢失。

### 为什么能量门在这台机器上不可靠
风扇是稳态噪声，Silero 偶尔判成语音、偶尔判成噪声；能量判据又要求
`rms >= max(0.012, floor*2.5)`，而 `floor` 在 0.01–0.05 之间抖动，
轻声说话时 `rms` 常常就在这条线上下。**两个判据都不可靠时，取交集只会更容易漏**。

### 改动
1. `TencentAsrBackend.needsContinuousAudio` 改回 **true**，KDoc 里写清两轮取舍：
   - 只送人声帧 → 服务端 VAD 听不到静默，永远不吐 `slice_type=2`，而且要额外靠本地计时；
   - 送静音帧 → 服务端会把噪声解成英文幻觉（p6-11 已由 `stripNoiseTail` 兜住）。
   - **结论：完整度优先**，噪声尾巴交给文本清理，不用音频门去赌。
2. **端点判据从「音频能量」改成「识别文本不再增长」**：删掉 `startStabilityWatch()`
   （每 200ms 轮询 `lastPartialAt`），改在 `onPartial` 里
   `if (clean != lastPartialText) { lastPartialText = clean; if (!finalized) armEndpoint() }`。
   理由：只有识别器知道「听到了新字」，能量只知道「有响声」。
   `endpointDelayMs()` 也随之从 `endpointMs + 400` 改成 `endpointMs`（不再等让服务端先判）。
3. `openBackend()` 装好后端后 `finalized = false`（原来只在 `enterAwake` 重置，
   第二轮会因 `finalized=true` 永远不收尾）。
4. `enterIdle` 兜底放宽成 `pendingText.isNotBlank() || partialText.isNotBlank()`，外面套 `stripNoiseTail`。
5. **删掉续说合并**（`continuationJob` / `CONTINUATION_TIMEOUT_MS` / `armContinuationTimeout`）：
   实机 20:22 那轮，final 之后紧跟一个噪声 partial 就把宽限取消了，
   `final → THINKING` 隔了 **3.5 秒**全靠续说超时兜底。现在行为确定：
   final → 等 `graceMs` → 交给模型；停顿超过「说完判定」就是新的一轮。

### 真机验证
```
20:23:47.658  → AWAKE (kws:小鲸)
20:23:50.156  TencentAsr: final: '住在杭州，做后端开发。'
20:23:50.700  grace 500ms 到期，交给 LLM: '住在杭州，做后端开发。'
20:23:50.702  → THINKING
20:23:53.165  → SPEAKING (mic off)
```
final 到交给模型 **544ms**（原来 3.5 秒），AWAKE 到开始思考 2.5 秒。

### 踩到的编译坑
Kotlin 表达式体里 `synchronized(lock) { ... }` 内不能 `return`（`Missing return statement`）；
这次则是按文本块删除时误留了一份 `flushPending` + `armContinuationTimeout`，
报 `Conflicting overloads` / `Unresolved reference 'continuationJob'` —— 改 Kotlin 用整段 `assert old in s` 定位比肉眼快。

## p6-13 主人角色卡「不生效」：不是没存进去，是指令被角色设定压掉了

### 现象
用户 m07056：`我这边将他对我的称呼改为SzTM，然后界面上显示生效但实际上我去询问他该怎么称呼我的时候，他还是我报以前的称呼主人`

### 排查
1. 先确认**有没有存进去**：`run-as ... cat shared_prefs/virtual_companion_settings.xml`
   ```
   <string name="persona">{"name":"sztm","nickname":"","background":"","preferences":""}</string>
   ```
   存了。`PromptBuilder` 也确实读了它 —— 所以不是「保存失败」这类老问题。
2. 再看 prompt 里这一行长什么样（新增 DEBUG 日志 `Log.i("Prompt", "system=\n" + system)`）：
   ```
   # 你对话的对象
   名字：sztm
   ```
   **只有一行「名字：X」，而上面角色设定里写着「你把用户当作唯一的『主人』」。**
   模型优先沿用角色设定里那个更有情感色彩的称呼，「名字：sztm」只是一条弱事实，
   于是继续喊「主人」。**用户眼里就是「改了没生效」。**

### 改法（`data/chat/ChatClient.kt` 的 `PromptBuilder.systemPrompt`）
不再只报事实，而是把三件事说清：
```
# 你对话的对象
他希望你称呼他为「sztm」。
说话时用这个称呼指代他；上面角色设定里出现的「主人」等词，指的就是他。
除非他明确要求换个叫法，否则不要改用别的称呼，也不要频繁重复称呼。
```
同时：
- `背景：` → `关于他：`，`喜好：` → `他的喜好与雷点（优先遵守）：`（后者明确优先级更高）。
- **补上「喜好与雷点」输入框**（`ui/settings/SettingsScreen.kt`）：`PersonaCard.preferences`
  从 p5 起就被 prompt 读取，但设置页从来没有暴露过它 —— 等于写死永远为空。
  原「背景 / 喜好」字段只写 `background`，容易让人以为喜好也写进去了。
- `buildMessages` 里加 `if (BuildConfig.DEBUG) android.util.Log.i("Prompt", "system=\n" + system)`：
  这类「角色卡生不生效」的问题，以后一条 `adb logcat -s Prompt` 就能定位，
  不用再靠 UI 上猜。

### 为什么不去改角色卡正文
用户的角色卡正文是**用户自己的创作**，里面有「主人」这种带人设的称呼。
让代码去正则替换用户文本是错的（会破坏语气），正确做法是在对象区把指代关系讲清。

### 验证（真机，`--es vc_text` 文字注入）
```
I/Prompt: 他希望你称呼他为「sztm」。
I/Prompt: 说话时用这个称呼指代他；上面角色设定里出现的「主人」等词，指的就是他。
```
问「你现在叫我什么名字？直接说出来，别绕。」→ 回复
**「sztm啊，还能叫啥，这名字我记得牢牢的。」**
（改前问同一句，回的是「主人」相关说法。）证据 `docs/proof/p6-13_persona_reply2.png`。

### 顺带加的调试入口
`adb shell am start -n <pkg>/.MainActivity --es vc_text "你好"`（仅 DEBUG）：
点击输入框 + 软键盘在 640×480 上坐标全乱（键盘一弹布局就上移，点「发送」经常点到模型身上，
反而触发「痒…你戳到我的尾巴了」），文字注入让这类验证稳定可重复。

### 追加：改成「主人」之后她又喊 sztm —— 第二个缺陷（旧回调闭包）
用户 m07154：`我现在又更改为主人，她还是叫我sztm`

先排除「没存进去」：prefs 已经是 `"name":"主人"`。**存了，也读了，但语音这条路读的是旧的。**

#### 真因
```kotlin
// 语音回调只挂一次
LaunchedEffect(voice) {
    voice.onUtterance = { text -> sendText(text) }
}
```
`LaunchedEffect(voice)` 的 key 永远是同一个 `voice` 实例，所以这段只跑一次，
lambda 被永久保存 —— 而 `sendText` 是 composable 里的局部函数，
**闭包里锁死的是第一次组合时的 `persona` / `character` / `settings` / `memory`**。

于是：
- 键盘输入 → `MainScreen(onSend = { sendText(it) })` 每次重组都是新 lambda → 立刻生效；
- 语音（以及 `--es vc_say` 调试旁路）→ 用 Activity 启动那一刻的快照 → 改了设置也不变。

这解释了为什么「界面上显示生效」但说话时还是旧名字 —— 两条入口读的不是同一份数据。

#### 改法
```kotlin
val latestSend by rememberUpdatedState<(String) -> Unit>({ t -> sendText(t) })
LaunchedEffect(voice) { voice.onUtterance = { text -> latestSend(text) } }
```
`vc_say` 的收集协程同样改用 `latestSend`。

#### 验证（运行中改称呼，不重启）
```
adb shell am start .../.MainActivity --es vc_persona "阿森"     # 调试钩子，见下
adb shell am start .../.MainActivity --es vc_say "你现在叫我什么？只回答那个称呼。"
I/Inject: persona name → '阿森' (in-session)
I/Prompt: 他希望你称呼他为「阿森」。
→ 回复「阿森，就这一个词，别的不说。」
```
证据 `docs/proof/p6-13_persona_inline.png`。改前同一条路径 prompt 里仍是「主人」

#### 关于提示词补的那句「这是**当前**的称呼」
用户这次是「sztm → 主人」，而历史对话里她刚连着喊了好几声 sztm。
模型会照着历史继续说旧称呼，所以必须点明当前值优先、历史里的旧称呼不要沿用。
这一句在「sztm → 主人」方向上是必需的（只写「称呼是X」会被历史压回去）。

#### 新增调试钩子
- `--es vc_persona "阿森"`：运行中改主人称呼（改设置要跟软键盘、滚动条搏斗，这条让回归可重复）。
- 上一轮临时加的 `--es vc_text` 已删除：仓库里本来就有 `--es vc_say`，重复了。

### 追加二：装的是新包，仍喊旧名 —— 第三个缺陷（历史把 system 压住了）
用户 m07241：`还是这样，你修改过后的应用重新安装上去了吗？`

先核对装机时间，避免「其实没装上」这种低级误判：
```
lastUpdateTime=2026-11-14 20:59:53   （含 commit 4be5275 的修复）
app-debug.apk  20:59  99685446 B
```
**装的是新包**，而且当轮 prompt 里确实是「他希望你称呼他为「主人」」——
可她的回答还是「阿森，就这个，别的我不说。」。

#### 真因
历史里最近几轮，她自己连着说了好几遍「阿森，就这一个词」「sztm啊」。
模型对**自己刚说过的话**服从度极高：system 开头的「现在的称呼是主人」被
紧挨着的对话记录压过去了。这不是 bug，是 LLM 的固有倾向
（离得越近的 token 权重越大）。

#### 改法：把运行时事实钉在用户输入前面
`data/chat/ChatClient.kt` 的 `buildMessages` 在 `picked`（历史）与 `user`（本轮输入）之间
插一条 system 提醒：

```kotlin
val address = ChatMessage.system(
    "（提醒：他现在的称呼是「${persona.displayName}」。历史对话里出现过的其他叫法都已作废。）",
)
out += system; memory?.let { out += it }; out += picked; out += address; out += user
```

只提醒「当前值」和「旧的作废」，**不要求她主动喊**（否则每句都带称呼，很吵）。

#### 验证（prompt 不变的前提下，历史里全是旧称呼）
```
问「你现在叫我什么？只回答那个称呼。」 → 「主人。」
问「今天好热啊，不想动。」            → 「主人别瘫着啦，热就开空调嘛，动一动都嫌累可不行。」
```
第二问是关键对照：称呼只在需要时出现一次，没有变成每句话都喊。
证据 `docs/proof/p6-13_pinned.png`、`docs/proof/p6-13_pinned2.png`。

#### 为什么一开始只改 system 就以为够了
我最初的两次验证都是**重启后再问**，历史很短；用户是**改完立刻连着对话**，
命中条件不同。这类「跟历史抢权重」的问题，必须在长历史下测才有意义。

### p6-14 角色卡「双份名字」：占位符、改名同步、冲突检测
用户 m07275：`在他的角色卡中。 既给他指定的名字，然后又在性格和人设中给他指定的名字，那修改不就对冲了吗？`

#### 这是真缺陷，不是误会
`CharacterCard.name` 是**字段**，而人设正文里的「你是「小鲸」」是**另一份手写文本**。
两处都参与拼 prompt（前者进「名字叫「X」」，后者原样进正文），
所以改字段不会动正文，模型读到的就是两个名字 —— 谁权重高谁赢，
实测就是正文里的那个赢（因为它是人设的一部分，语气更强）。

设备上的实际状态：
```
name      = 小爱
wakeWord  = 小爱
description = 你是「小鲸」，一只化成人形的深海鲸娘……
```

#### 三层处理，从「以后不会再犯」到「已经犯了的怎么办」
1. **占位符（治未来）**：`ChatClient.fillNames(text, charName, userName)` 把
   `{{char}}`/`{{Char}}`/`{{CHAR}}` 换成角色名、`{{user}}`/`{{User}}`/`{{USER}}` 换成
   主人称呼，`description/personality/scenario/exampleDialogue/systemPromptExtra`
   全部先过这一层。正文里写 `{{char}}` 就永远跟着字段走。
   字段下方加了灰字说明：「正文里写 {{char}} 代指她、{{user}} 代指你；用占位符的话，改名不用回头改正文。」
2. **改名同步（治已经写死名字的）**：名字输入框 `onCommit` 时，若 `old != fresh`，
   对正文六个字段执行 `text.replace(old, fresh)`。改一次名字，正文跟着改。
3. **冲突检测（治改过名但没被同步的）**：`Regex("「([^」\n]{2,6})」")` 扫正文，
   剔除当前名字与主人称呼，按出现次数取前两条，显示琥珀色提示
   「正文里还写着「X」，和上面这个名字对不上。」+ 一行蓝字可点
   「把正文里的「X」都改成「Y」」，点一下执行同样的替换。
   **不做自动替换** —— 人设是用户自己写的，静默改字比提示更危险。
   标题也改成跟着字段走：`角色卡（小爱）` 而不是写死「小鲸」。

#### 验证
- 点击「把正文里的「小鲸」都改成「小爱」」→ 提示行消失，正文变成
  「你是「小爱」，一只化成人形的深海鲸娘……」，落盘确认（`shared_prefs` 里 `description` 已是「小爱」）。
  证据 `docs/proof/p6-14_char_card_fixed.png`。
- 占位符路径：直接把 prefs 里的正文改成 `你是{{char}}，一只化成人形的深海鲸娘……`，
  冷启动发一轮，`Prompt` 日志读到 `你是小爱，一只化成人形的深海鲸娘。` —— **替换生效**。
  测完把 prefs 还原。
- prompt 侧：`你现在扮演一个虚拟伴侣角色，名字叫「小爱」。` + 正文「小爱」，两处一致。

#### 一个踩坑

### p6-15 名字只留一个来源：正文里不再出现名字
用户 m07349：`如果这样子的话如果我给其他人使用的话，他们不懂得怎么去书写正文，会引发错误。`
接一句定调（m07460）：`因位正常已经在上面填了名字的话。一般人就不会在人设再填一个名字，所以说不用做那么多防御。只需要移除设定中的名字，名字只由上面的名字输入框决定即可。`

#### 上一版做多了
p6-14 为了「正文写死名字」做了三层防御：占位符提示、改名同步、
引号名字冲突检测 + 一键统一 + 保存确认弹窗。方向对，但对普通用户是噪音：
一屏里出现 `{{char}}`、琥珀色警告、可点蓝字，反而更像出错提示。

#### 这一版的做法：让名字没有第二个位置
1. **默认人设正文里不出现名字**（连占位符都不出现）：
   ```
   你是一只化成人形的深海鲸娘。你有一头深蓝色长发和一条漂亮的鲸尾。
   你把对方当作唯一在意的人，喜欢黏着他，说话带一点点撒娇和吃醋。
   …
   ```
   名字由 `PromptBuilder` 统一加：`你现在扮演一个虚拟伴侣角色，名字叫「小鲸」。`
2. **默认开场白也不写名字**：`回来啦？我一直在等你呢。`
3. **删掉**：冲突检测整段、可点「一键统一」、保存确认弹窗、`literalNameInBody()`。
4. **保留**（都是静默、零打扰的）：
   - `PromptBuilder.fillNames()` 支持 `{{char}}`/`{{user}}`，给会写的人用，默认文本不用；
   - 改名时对正文做一次 `replaceInBody(old, fresh)` —— 默认卡里正文没有名字，这一步是空操作，
     留着只为兼容用户自己写过名字的旧卡。
5. 界面提示收敛成一句：`名字只在上面这一处填，正文里不用再写名字。`

#### 顺手挖出一个真 bug（这次改动的直接收益）
角色卡标题是 `角色卡（${character.name}）`，而 `Section` 的
`rememberSaveable(title)` / `remember(title)` **全都拿 title 当 key**。
改名字 → 标题变化 → key 变化 → 这一组自己收回、`baseline` 重置、
「保存本组」再也不出现（实测：改完名字后整组折叠、按钮消失）。
修法：`Section` 增加 `key: Any? = title` 参数，角色卡传 `key = "character"`。
这类「用会变的字符串当状态 key」的坑，只有在真机上改一次名字才会暴露。

#### 验证
- 默认卡：名字 `小鲸`、正文无名字、开场白 `回来啦？我一直在等你呢。`（`docs/proof/p6-15_card_no_name.png`）
- 真实 prompt（`adb logcat -s Prompt`）：
  ```
  你现在扮演一个虚拟伴侣角色，名字叫「小鲸」。
  # 你的角色设定
  你是一只化成人形的深海鲸娘。…
  你把对方当作唯一在意的人，…
  # 说话风格示例
  主人：今天好累啊。
  小鲸：累就先把包扔了，过来坐这儿。…
  ```
  名字只在第一行出现一次；示例对话里的 `{{user}}`/`{{char}}` 正确解析成「主人」「小鲸」。
- 改名字为「小」后：标题变 `角色卡（小）`、这一组**保持展开**、`保存本组` 正常出现。

### p6-16 改名不生效：不是模型的问题，是草稿没提交
用户 m07516：`又和之前一样，改名后角色不认新名字。`

#### 先分清是哪一层
两种可能：①提示词里还是旧名字（没提交/没落盘）；②提示词已是新名字、
模型仍自称旧名（历史锚定）。做法是用 prefs 直接写名字，绕开 UI 做对照：

```
改 prefs: character.name = 阿蓝 → 冷启动 → 问「你叫什么名字」
Prompt: 你现在扮演一个虚拟伴侣角色，名字叫「阿蓝」。
回复:   阿蓝。怎么，才几天就把我名字忘了？
```

**提示词链路完全正常**，模型也认新名字。所以问题在「UI 改名有没有写进状态」。

#### 根因：草稿只在失焦时提交
`ui/settings/SettingsScreen.kt` 的输入框为了不每敲一个字就落盘，用的是
「本地草稿 + 失焦提交」：

```kotlin
.onFocusChangedCompat { isFocused ->
    if (focused && !isFocused && draft != value) onCommit(draft)
    focused = isFocused
}
```

但失焦事件并不保证发生：
- 点「保存本组」按钮 —— Compose 里点 Button **不会**让文本框失焦；
- 直接按返回键离开设置页 —— 节点被销毁，但 `onFocusChanged(false)` 不一定派发。

两种走法都是「输入框里显示新名字、prefs 里还是旧名字」，回到聊天自然还是旧名。

#### 三处改动
1. 保存按钮先 `focus.clearFocus()` 再 `onSave()`，把提交顺序钉死；
2. 两个输入框都插 `CommitOnDispose(draft, value, onCommit)`（`DisposableEffect` +
   `rememberUpdatedState`），离开组合时把没交出去的草稿补交；
3. `SettingsStore.updateCharacter()` 加 `if (next == before) return` ——
   失焦提交与兜底提交会各触发一次，实测出现 `name '阿' → '阿'` 的无意义写入。

顺带加了 `CardStore` 日志（`character: name '旧' → '新'`、`sendText: card=...`），
这类「界面改了但没生效」的问题，以后看一眼日志就能分清是哪一层。

#### 验证
```
改前：改成「阿」→ 点返回 → 冷启动问名字 → Prompt 仍是「阿蓝」   ✗
改后：改成「阿」→ 点返回 → CardStore: name '阿蓝' → '阿'
      → Prompt: 名字叫「阿」→ 回复「阿。就一个字，记好了哦。」  ✓
```
截图 `docs/proof/p6-16_rename_ok.png`；测完把设备名字/唤醒词还原成「小鲸」。
