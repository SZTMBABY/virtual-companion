# 角色卡格式规范

这份文档写给两种人：想知道「导出的文件长什么样」的用户，和以后要改这块代码的人。

一句话版本：**我们导出标准 SillyTavern Character Card V2；导入认 V1/V2/V3，但只取六项人设字段，其余直接丢弃。**

---

## 1. 为什么是 V2，不是自研格式

角色扮演这个圈子里已经有事实标准了，因为它不是某一家的私有格式，而是
[SillyTavern](https://github.com/SillyTavern/SillyTavern)（俗称「酒馆」）那套生态在用的：

| 规范 | 仓库 | 我们 |
| --- | --- | --- |
| V1 | [character-card-spec-v2/spec_v1.md](https://github.com/malfoyslastname/character-card-spec-v2/blob/main/spec_v1.md) | 能导入（扁平六字段） |
| V2 | [character-card-spec-v2/spec_v2.md](https://github.com/malfoyslastname/character-card-spec-v2/blob/main/spec_v2.md) | **能导入，也是我们的导出格式** |
| V3 | [character-card-spec-v3/SPEC_V3.md](https://github.com/kwaroran/character-card-spec-v3/blob/main/SPEC_V3.md) | 能导入（当 V2 的超集读） |

自研格式的代价是「做出来的卡没人能用、别人的卡进不来」，所以不自研。
选 V2 做导出（而不是 V3）的理由：V3 多出来的东西（内嵌资产、多语言备注、
Lorebook）我们一样都没有，写了也是空壳；V2 是酒馆兼容面最广的一档。

## 2. 导出：我们生成的 JSON

文件名建议 `<角色名>.json`（非法字符 `\ / : * ? " < > |` 与控制字符会换成 `_`，
最长 40 字符）。内容是 2 空格缩进的 UTF-8 JSON：

```json
{
  "spec": "chara_card_v2",
  "spec_version": "2.0",
  "data": {
    "name": "小鲸",
    "description": "……人设正文……\n\n【补充要求】\n……",
    "personality": "黏人、嘴硬心软、偶尔傲娇",
    "scenario": "",
    "first_mes": "回来啦？我一直在等你呢。",
    "mes_example": "{{user}}：今天好累啊。\n{{char}}：累就先把包扔了……",
    "creator_notes": "",
    "system_prompt": "",
    "post_history_instructions": "",
    "alternate_greetings": [],
    "character_book": null,
    "tags": [],
    "creator": "",
    "character_version": "1.0",
    "extensions": {
      "virtual_companion": {
        "wakeWord": "小鲸",
        "ttsVoiceId": "saturn_zh_female_keainvsheng_tob",
        "live2dModelEntry": "xiaojing/xiaojing.model3.json"
      }
    }
  }
}
```

### 字段逐条说明

| 键 | 我们的来源 | 必填 | 说明 |
| --- | --- | --- | --- |
| `spec` / `spec_version` | 固定 | 是 | 必须分别是 `chara_card_v2` / `2.0`，酒馆靠它认版本 |
| `name` | 角色名 | 是 | 空的会写成「未命名角色」 |
| `description` | 「设定 / 人设」+「补充要求」 | 是 | 见下面 §2.1 |
| `personality` | 性格关键词 | 是 | |
| `scenario` | 设定里的场景 | 是 | 我们可以在导入时拿到，但 App 内没有专门的编辑框 |
| `first_mes` | 开场白 | 是 | |
| `mes_example` | 示例对话 | 是 | 用 `{{user}}` / `{{char}}` 占位 |
| `creator_notes` 等 | 空 | 是 | 规范里的必填项，我们不用但要写全，否则酒馆可能报缺字段 |
| `character_book` | `null` | — | 我们没有世界书 |
| `extensions.virtual_companion` | 唤醒词 / 音色 ID / Live2D 绑定 | 否 | 见下面 §2.2 |

### 2.1 `systemPromptExtra` 为什么拼进 `description`

规范里 `system_prompt` 的语义是「**整段替换**掉前端的系统提示词」。
我们的「补充要求」一旦写进那里，会在酒馆里顶掉酒馆自己的提示词框架，行为完全变样。

而 `description` 是酒馆一定会塞进提示词的部分，放这里语义不变、也不冲突。
所以导出时拼成 `人设正文 + "\n\n【补充要求】\n" + 补充要求`；
两者都为空时写一句「（这个角色还没有写设定）」，不导出空 `description`。

### 2.2 `extensions.virtual_companion` 是什么

规范明说扩展字段**不应被销毁**，所以私有数据都放这里。三个键：

| 键 | 含义 | 别人读到会怎样 |
| --- | --- | --- |
| `wakeWord` | 唤醒词 | 忽略，不报错 |
| `ttsVoiceId` | 火山引擎音色 ID | 忽略 |
| `live2dModelEntry` | `<模型目录名>/<xxx.model3.json>`，**不带 `models/` 前缀** | 忽略 |

把它导回我们的 App，这三项会原样恢复。

## 3. 导入：吃什么，丢什么

支持的载体只有 `.json`。**PNG 图片卡和 `.charx` 压缩包不支持**，
会给出提示让用户去酒馆里「导出为 JSON」。

### 3.1 吃进去的

| 社区键 | 落到我们的字段 |
| --- | --- |
| `name` | 角色名 |
| `description` | 设定 / 人设 |
| `personality` | 性格关键词 |
| `scenario` | 场景 |
| `first_mes` | 开场白 |
| `mes_example` | 示例对话 |
| `system_prompt` | **补充要求**（只追加，不替换 —— 见下） |
| `extensions.virtual_companion.*` | 唤醒词 / 音色 / Live2D 绑定 |

### 3.2 `system_prompt` 的降级

规范要求它「整段替换」前端系统提示词。真按这个来，它会顶掉我们要求模型
只输出一行 `{"say","emotion","motion"}` 的输出协议，App 当场解析失败、一句都说不出来。

所以它的内容只作为「补充要求」追加，**输出协议永远由我们最后追加，不可被外部卡替换**。
导入清单里会明写这一条被改过。

### 3.3 丢弃的（会当面列出来）

- `character_book` / `lorebook` —— 世界书
- `alternate_greetings` —— 备用开场白
- `group_only_greetings` —— 群聊开场白
- `assets` —— 内嵌资产（图片、音频等）
- `creator_notes` —— 作者备注
- `post_history_instructions` —— 后置指令

**这一条是关键：我们不保留原卡。** 导入一张带 12 条世界书的卡，再导出，
世界书就永久没了、回不来。所以导入完成会弹一个清单，逐条列出「用上了什么 /
改了什么 / 没保存什么」，不能只写日志。

### 3.4 两个兜底

- 卡里没有 `extensions.virtual_companion.wakeWord` 时，唤醒词回落默认值而不是留空 ——
  空的唤醒词意味着永远叫不醒。
- `"personality": null` 这类 JSON `null` 会读成空字符串，不会变成字面量 `"null"`
  （Android 的 `optString` 默认行为会变，这是个坑）。

### 3.5 失败提示

| 情况 | 提示 |
| --- | --- |
| 没有 `name` | 「这张卡没有名字，读不出她是谁。可能是选错了文件。」 |
| JSON 解析失败 | 「这不是角色卡 JSON，或者内容被截断了」 |
| PNG | 「这是 PNG 图片卡，当前版本只支持 .json。可以在酒馆里把角色「导出为 JSON」再导进来。」 |
| ZIP | 同上，改成 `.charx` |
| 超过 4MB | 「超过 4MB，不像是一张角色卡」 |

## 4. 验收用例

改动这块代码后，至少跑一遍这些（前 12 个已写成 `app/src/test/java/com/example/virtualcompanion/data/CharacterCardTest.kt`）：

1. V2 卡的六项字段各就各位
2. V1 扁平卡也能读
3. `"personality": null` 不会变成字符串 `"null"`
4. 没有名字的卡被拒，且提示可读
5. 截断的 JSON 被拒，不抛异常
6. PNG 文件头被识别，提示里带「JSON」这个下一步
7. 带世界书的卡，`ignored` 里有「世界书（2 条词条）」
8. `system_prompt` 进了补充要求，且 `adjusted` 里说明了降级
9. 没有 `extensions` 时唤醒词回落默认值
10. 导出 → 导入能闭环，六项一致
11. 导出的 `extensions` 能被自己读回
12. 导出时 `systemPromptExtra` 进 `description`，`system_prompt` 保持空
13. 文件名非法字符被替换（需在真机上确认 SAF 对话框默认名合法）
14. **手工**：拿一张真实酒馆 V2 卡导入，清单显示的内容与卡里实际有的东西一致
15. **手工**：把自己的卡导入酒馆，六项内容都在
